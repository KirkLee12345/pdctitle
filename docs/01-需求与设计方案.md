# 01 · 需求与设计方案（v2：多称号模型）

> 目标版本：Minecraft **26.2**（Fabric，稳定版）｜ 依赖：**仅 Fabric Loader（零 fabric-api）** ｜ 模式：纯服务端模组，**原版客户端可直接加入**。

## 1. 需求汇总（已确认）

1. 服务端为 Fabric 26.2，需要“称号”功能。
2. 称号由 **OP 授予/收回**；**普通玩家自己选择佩戴/不佩戴**。
3. 一名玩家可以拥有 **0..N** 个称号，且**至多佩戴 1 个**（可为 0 = 不佩戴，此时完全显示原名）。
4. 佩戴的称号要显示在玩家名字之前，覆盖三处：
   - 聊天栏消息的玩家名
   - Tab 列表的玩家名
   - 头顶悬浮名牌的玩家名
5. 纯服务端实现（聊天栏走“拦截重发”，不做客户端混合方案）。

## 2. 总体决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 客户端要求 | 无（原版即可） | 三通道全部在服务端侧实现/驱动 |
| 依赖 | 仅 fabric-loader（自带 Mixin） | 需求小、零依赖；不走 fabric-api 事件 |
| 权限模型 | 授予=OP；佩戴=玩家自助 | 见 §4 |
| 数据模型 | UUID → { owned 称号集, equipped } | 见 §3 |
| 存储 | JSON 文件 + 原子写 | 简单、可读、可备份 |
| 三个显示通道 | 相互独立，分别实现 | 机制完全不同，见 §5 |

## 3. 数据模型

内存：`Map<UUID, PlayerData>`（`TitleStore`，单例、synchronized）。
`PlayerData`：`Set<TitleData> owned` + `TitleData? equipped`。
`TitleData`：record，字段 `display`（带 `&` 颜色码的原文案，例如 `&b[至尊]`）。

不变式：
- 同文案对同一玩家只算一条（重复授予提示“已拥有”）；
- `equipped ∈ owned ∪ {null}`；
- 收回正佩戴的称号 → 自动卸下；
- 玩家离线也可被授予/收回（按 UUID 存储，改名不掉称号）。

## 4. 权限模型

| 操作 | 允许者 | 范围 |
|---|---|---|
| grant / set（授予，set=授予+佩戴）/ revoke / clear / list他人 | OP（permission level ≥ 2） | 任意玩家（含离线） |
| wear / unwear / my | 任意玩家 | 仅限**自己拥有的**称号 |
| 佩戴解析 | 精确匹配 own 中的原文案 | 歧义不存在（每玩家文案唯一） |

> 说明：OP 也可以戴自己拥有的称号；佩戴操作不区分玩家，只校验“是否拥有”。

## 5. 三个显示通道的技术方案

### 5.1 头顶名牌 —— Scoreboard Team（原生机制）

- 玩家**佩戴**称号时：进入专属队伍（队名 `titlemod_<uuid片段>`，需通过 26.x 队名规则），
  用 `Team#setPlayerPrefix` 设为“佩戴称号的展示文本”；玩家**卸下/收回佩戴**时从队伍移除。
- Team 数据由服务端随 Scoreboard 同步给所有客户端，**客户端自动渲染**头顶前缀，无需任何额外代码。
- 注意：若玩家已被其它玩法/数据包占用队伍，需先检测；已占用则合并前缀或打日志告警（私服通常无冲突）。
- 显示文本 = 前缀(称号) + 玩家名；客户端若开启“Always Show Nameplates”等设置与队伍无关。

### 5.2 聊天栏 —— 拦截重发（1.19.1+ 签名限制的对策）

- **限制事实**：1.19.1+ 玩家聊天消息带签名，客户端校验后显示名必须等于签名内的档案名；
  服务端**无法**在保留签名有效性的前提下改写消息头的显示名（伪造会被标“不可信”）。
- **对策**：在聊天广播的单一入口拦截原消息 → 取消发送 → 服务端以**系统消息**形式向全体重发一条
  自组装的行：`<佩戴称号> <玩家名>: <消息内容>`。
  系统消息在聊天栏以普通样式渲染，**不出现** “Not Secure/已修改” 角标。
- **无称号玩家不拦截**（原样走原版签名聊天，零影响）。
- 实现位置二选一（推荐 A）：
  - A. Mixin 进聊天广播入口（如 `PlayerList#broadcastChatMessage`，26.2 方法名 M0 确认）；
  - B. 回退方案：引入 fabric-api 的 `ServerMessageEvents.ALLOW_CHAT_MESSAGE` + 自行广播。
- 权衡：失去“点击名字/聊天举报”等签名聊天附属能力 —— 私服可接受；如果日后想保留，
  可切“服务端+客户端混合”渲染方案（docs/03 §6 有说明）。

### 5.3 Tab 列表 —— 覆写列表显示名 + 主动刷包

- 澄清：现代版本 Team prefix **不会**显示在 Tab，Tab 只显示玩家档案名或服务端单独下发的 displayName。
- 方案：
  1. **覆写来源**：Mixin `ServerPlayer#getTabListDisplayName()`（26.2 名称 M0 确认；Yarn 时代叫
     `ServerPlayerEntity#getPlayerListName()`），有佩戴称号时返回 `称号 + 名字` 组件。
     这样“新玩家进服看到的全量 PlayerList 包”自动带对所有人的称号。
  2. **主动刷新**：称号变更（佩戴/卸下/收回）后，向所有在线玩家广播
     `ClientboundPlayerInfoUpdatePacket(Action.UPDATE_DISPLAY_NAME, 目标玩家条目)`。
- 时序兜底：JOIN 时“别人看到新玩家”的条目可能已先发出，故加入服钩子里对新玩家补发一次刷新。

### 5.4 通道总开关（TitleConfig）

服务器级配置 `chat / tab / nametag` 三个布尔总开关（默认 true）。单玩家不再单独配置通道，
显示与否只由“是否佩戴”决定；总开关用于整服关闭某通道。

## 6. 存储格式（titles.json，v2）

`config/titlemod/titles.json`：

```json
{
  "a1b2c3d4-e5f6-7890-abcd-ef1234567890": {
    "owned": ["&b[至尊]", "&a[创世元老]"],
    "equipped": "&a[创世元老]"
  },
  "b2c3d4e5-...": {
    "owned": []
  }
}
```

- `equipped` 省略/为空 = 不佩戴；
- `owned` 空数组 = 玩家存在但无称号（也可整体不写该玩家记录）。

## 7. 生命周期与风险

| 时机 | 动作 |
|---|---|
| 服务端启动 | `TitleStore.load()`，装配 Service/指令 |
| 玩家 JOIN / 重生 | 断言名牌队伍、Tab 补发刷新（幂等） |
| 佩戴 / 卸下 / 授予 / 收回 | 更新内存 → 落盘 → 刷新该玩家三通道 |
| 服务端停止 | `save()` |

风险清单（详见 docs/03 §7）：
1. 26.x 反混淆版本 API 名需在 M0 用 mcsrc.dev 实测核对；
2. 队伍被其它玩法占用；
3. 与其它聊天类模组共存时的“双发”；
4. 称号文本注入（换行/控制符）→ 构造时 sanitize；
5. 大版本升级需重编（26.x 起模组不再向前兼容，代码量小，迁移可控）。
