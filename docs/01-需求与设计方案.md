# 01 · 需求与设计方案（v3：称号池 + 归属 + 佩戴 + 悬停描述）

> 目标版本：Minecraft **26.2**（Fabric，稳定版）｜ 依赖：**仅 Fabric Loader（零 fabric-api）**｜ 纯服务端模组，**原版客户端可直接加入**。

## 1. 需求汇总（已确认）

1. 服务端为 Fabric 26.2，需要“称号”功能。
2. **称号池**：OP 可维护一个全局称号列表 —— 添加 / 修改（显示文案、描述）/ 删除 / 查看。
3. **归属**：OP 把池中称号**授权**给某个玩家；授权后才能佩戴，方便把同一称号发给很多玩家。
4. 删除称号后，所有玩家的该称号**随之消失**（佩戴中的自动卸下）。
5. **佩戴**：玩家自己选择佩戴自己拥有的某个称号，或**不佩戴**（0..N 拥有，至多佩戴 1 个，可为 0）。
6. 每条称号带**描述**（介绍该称号）。
7. 聊天栏中玩家名前的称号：**鼠标悬停显示描述**（类似成就/进度的悬停提示样式）。
8. 称号显示在玩家名之前，覆盖：聊天栏 / Tab 列表 / 头顶名牌 三处（纯服务端实现，聊天走拦截重发）。

## 2. 总体决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 数据权威源 | 称号池 definitions（单一来源） | 同一称号发多人只需一次授权；删除/修改全局生效 |
| 存储 | 两个 JSON：definitions.json + players.json | 池与玩家数据分离，职责清晰，均原子写 |
| 客户端要求 | 无 | 三通道全在服务端实现/驱动 |
| 依赖 | 仅 fabric-loader（自带 Mixin） | 零 fabric-api |
| 权限模型 | 池管理+授权=OP；佩戴=玩家自助 | 见 §4 |
| 三显示通道 | 相互独立实现 | 机制完全不同，见 §5 |

## 3. 数据模型

### 3.1 称号池（TitleDefinition）

`Map<String, TitleDefinition>`（`TitleStore` 持有）：
- key = `id`（^[a-z0-9][a-z0-9_-]{0,31}$，唯一、不可变）；
- value = `TitleDefinition(display, description)`：
  - `display`：带 `&` 颜色码的显示文案（≤32，如 `&b[至尊]`）；
  - `description`：纯文本描述（≤128，不解析 &，用于悬停）。

### 3.2 玩家（PlayerData）

`Map<UUID, PlayerData>`：
- `owned: Set<String>` —— 被授权的池 id 集合（0..N，顺序稳定）；
- `equipped: String?` —— 佩戴中的池 id（∈ owned ∪ {null}）。

### 3.3 不变量与级联

- `equipped == null || owned.contains(equipped)`；
- 同一称号对同一玩家只能授权一次；
- 收回授权 / 池条目删除 → 若正佩戴则自动卸下；
- 池条目删除 → `TitleStore.removeDefinition(id)` 遍历所有玩家级联清除并返回受影响 UUID 列表；
- 池条目改文案/描述 → 无需碰玩家数据，展示时实时解析，全服立即生效；
- 玩家按 UUID 存储，改名不掉授权；离线也可被授权/收回，上线自动生效。

## 4. 权限模型

| 操作 | 允许者 | 范围 |
|---|---|---|
| 池管理：add/edit/desc/remove/list/info/who | OP（level≥2） | 全局定义 |
| 归属管理：grant/set/revoke/clear | OP | 任意玩家（含离线） |
| 佩戴/卸下/查看自己：wear/unwear/my | 任意玩家 | 仅限**自己已被授权**的称号 |

## 5. 三个显示通道 + 悬停描述

### 5.1 头顶名牌 —— Scoreboard Team（原生）

- 佩戴时进专属队伍（`pdctitle_<uuid片段>`），`Team#setPlayerPrefix` = 解析后的 display；卸下/无授权即移出。
- 进队前检测是否已被别的玩法占用队伍：占用则合并前缀或告警跳过（私服默认告警跳过）。
- Team 数据随 Scoreboard 同步，**所有原版客户端自动渲染头顶前缀**。
- 显示 = `前缀(称号) + 玩家名`。头顶不可悬停，故无描述展示。

### 5.2 Tab 列表 —— 覆写列表显示名 + 主动刷包

- 澄清：现代版本 Team prefix 不显示在 Tab；Tab 显示档案名或服务端下发的 displayName。
- Mixin `ServerPlayer#getTabListDisplayName()`：佩戴时返回 `称号+名字` 组件（新进服玩家的首屏自动正确）；
- 佩戴/卸下/收回后向所有在线玩家广播 `ClientboundPlayerInfoUpdatePacket(Action.UPDATE_DISPLAY_NAME, 目标条目)`；
- JOIN 钩子对新玩家补发一次（时序兜底）。Tab 无悬停，故只显示称号名。

### 5.3 聊天栏 —— 拦截重发 + 称号悬停描述（核心新增）

**背景**：1.19.1+ 玩家聊天带签名，显示名与签名绑定，服务端无法直接改；对策 = 在广播入口拦截原消息 →
取消 → 服务端以**系统消息**重发自组装行：`<称号> <玩家名>: <内容>`（无 “Not Secure” 徽标）。

**悬停描述**：因为整行是服务端组件，可自由构造：
- “称号”文本块解析 display（含颜色），并挂 `HoverEvent(SHOW_TEXT)`；
- 悬停内容模仿成就/进度提示：第一行称号显示名（带颜色），第二行描述（灰色斜体小字）；
- 无佩戴称号的玩家：不拦截、放行原版签名聊天，零影响。

> 悬停仅聊天栏可用（Tab/头顶无悬停），符合需求“聊天栏玩家名前面的称号悬停显示描述”。

### 5.4 通道总开关

服务器级配置 `chat/tab/nametag` 布尔总开关（默认全开，规划中 TitleConfig）；单玩家无需单独配通道，
显示与否只由“是否佩戴”决定。

## 6. 存储格式（两个文件，v3）

`config/plttitle/definitions.json`：

```json
{
  "legend":  { "display": "&b[至尊]",   "description": "开服最早一批元老玩家的纪念称号" },
  "founder": { "display": "&a[创世元老]", "description": "为服务器建设做出重大贡献的玩家" }
}
```

`config/plttitle/players.json`：

```json
{
  "a1b2c3d4-e5f6-7890-abcd-ef1234567890": {
    "owned": ["legend", "founder"],
    "equipped": "founder"
  }
}
```

- `owned`/`equipped` 存的是**池 id**；
- 加载时清理指向不存在 id 的脏数据（比如手工误删池文件）；
- 写盘：临时文件 + 原子移动，防崩溃损坏。

## 7. 生命周期与风险

| 时机 | 动作 |
|---|---|
| 服务端启动 | load 两个文件 → 装配 Service/指令 |
| JOIN / 重生 | 断言名牌队伍、Tab 兜底补发（幂等） |
| 池条目 增/改/删 | 改：全服即时生效（无额外动作）｜删：级联清理 + 刷新受影响在线玩家 |
| grant/revoke/clear/wear/unwear | 更新内存 → 落盘 → 刷新该玩家三通道 |
| 服务端停止 | save() |

风险清单（详见 docs/03 §7）：
1. 26.x 无混淆，API 名在 M0 用 mcsrc.dev 实测核对；
2. 队伍被其它玩法占用；
3. 与其它聊天模组共存的双发；
4. 文本注入 → 统一经 TitleDefinition 清洗（控制字符剥除 + 长度上限）；
5. 大版本升级需重编（代码量小，迁移可控）。
